# PinyinDuck for Android

An Android input method (IME) for typing Mandarin pinyin and picking Chinese characters
with the English definition next to every candidate — the idea behind
[PinyinDuck](../README.md) and TypeDuck, running as a real keyboard on a real device.

Type `nihao` and the strip offers 你好 *"hello; hi"*, 你 *"you"*, 呢 *"dense wool fabric"*
all the way down, and **▴** opens the full list, where each one also carries its tone-marked
pinyin. The definition is the point: 你 and 泥 look identical and
mean nothing alike, so a learner should never have to guess.

This is **Milestone 3** of [PLAN.md](../../PLAN.md): the same dictionary engine and the same
`dictionary.btree` asset as the web app, wrapped in an `InputMethodService`.

## Requirements

| | |
| --- | --- |
| Device | Android 8.0 (API 26) or newer |
| Build JDK | 17 or newer (tested on 21) |
| Android SDK | Platform 35 and Build-Tools 35.0.0 |

The app needs no network permission and makes no network calls. The dictionary ships inside
the APK, so it works in airplane mode.

## Building

The dictionary is generated by `packages/core` and already committed at
`packages/web/public/dictionary.btree`. The Android build copies that same file into the
APK, so there is only ever one dictionary in the repository. If it is missing, the build
stops with a message telling you to run `npm run build:dict`.

Point Gradle at your SDK, either with the environment:

```bash
export ANDROID_HOME="$HOME/Android/Sdk"
```

or with `sdk.dir` in `packages/android/local.properties`:

```properties
sdk.dir=/home/you/Android/Sdk
```

Then build. This is a Gradle project, so Gradle builds it:

```bash
cd packages/android
./gradlew assembleDebug
```

The APK lands at:

```
packages/android/app/build/outputs/apk/debug/app-debug.apk
```

On Windows use `gradlew.bat` instead of `./gradlew`.

| Task | What it does |
| --- | --- |
| `./gradlew assembleDebug` | The debug APK |
| `./gradlew test` | Unit tests, including the engine parity test |
| `./gradlew jacocoTestReport` | Coverage report (HTML and XML) |
| `./gradlew check` | Tests plus the coverage floor |
| `./gradlew lintDebug` | Android Lint |
| `./gradlew assembleRelease` | Release build |

There is a `package.json` here only so `npm install` at the repository root recognises
`packages/android` as part of the workspace. It defines no scripts, and the Android package
is deliberately kept out of the root `npm run build` and `npm test`, so neither needs an
Android SDK installed.

## Installing

### Over ADB

```bash
adb install -r packages/android/app/build/outputs/apk/debug/app-debug.apk
```

### By hand

Copy `app-debug.apk` to the phone and open it. Android will ask you to allow installs from
your file manager the first time. Debug builds are signed with the standard debug key, so
they install without any signing setup.

### Enable it

Installing is not enough — Android keeps keyboards switched off until you turn one on:

1. **Settings → System → Languages & input → On-screen keyboard**.
2. Tap **Manage on-screen keyboards** (wording varies by Android version and skin).
3. Enable **PinyinDuck**.
4. Go back and set **PinyinDuck** as the current keyboard, or press the 🌐 globe key while
   typing to switch to it.

There is also a **PinyinDuck** launcher icon that opens a settings screen with the script
default and a dictionary health check, and a button that jumps straight to the system
keyboard settings.

> If PinyinDuck does not appear in the list, it is usually because the install was
> interrupted or the APK was rebuilt without reinstalling. Uninstall and reinstall it.

## Using it

### Typing

Tap letters to build a pinyin syllable. The composition bar shows what you have typed, the
strip below re-ranks on every keystroke, and the pinyin appears in the app's text field as
you type — exactly what you see in the strip.

Tap a candidate to commit it. **If the candidate only covers the start of what you typed,
the rest stays buffered**, so tapping 你 part-way through `nihao` leaves `hao` ready and the
next tap finishes the word:

```
type:   n i h a o
tap 你  →  你 | hao        (buffer continues)
tap 好  →  你好
```

### Keys

| Key | While composing | While not composing |
| --- | --- | --- |
| `space` | Commit the highlighted candidate | Insert a space |
| `⌫` | Delete the last buffered letter | Delete before the cursor |
| `↵` | Send the field's own action (Enter, Search, …) | Same |
| `✕` | Abandon the composition and remove the pinyin | — |
| `1`–`5` | **Tone number** | Insert the digit |

A **digit during a composition is a tone number**, not candidate selection: type `shi` then
`4` and the strip narrows to shì. This is the one deliberate difference from the web
playground, where the number keys are taken by candidate selection for the whole
composition and tone numbers are therefore unreachable. On a phone you pick candidates by
tapping, so the number row is free to carry tones.

If nothing matches at all — `qqq` finds no candidates — space leaves the typed letters in
the field as ordinary text, so you are never stuck.

Hold **⌫** to delete repeatedly.

### Candidates

The strip shows four candidates with page arrows either side, each pairing the characters with
their definition. **▴** opens the full list, which lays the candidates out two per row with the
tone-marked pinyin, the **HSK level** and the English gloss for each one, and scrolls through
everything the session fetched. **▾** collapses it again. That expanded view is the screen worth
reading when two characters sound the same and you want to know which is which.

**简 / 繁** switches every candidate between Simplified and Traditional without losing the
composition, and **✕** clears it.

### Layers

`?123` opens the digits, `?#+=` the symbols, and **ABC** comes back to letters.

### Hardware keyboard

A physical keyboard works too, driving the same composition rules as the on-screen one:
letters, digits, `space`, `backspace`, `enter`, `escape` (cancels the composition), and the
arrow keys — left/right move the selection, up/down move by a page. That also makes the app
testable from a terminal:

```bash
adb shell input text nihao      # note: `adb shell input text` bypasses the IME, so use
                                # `adb shell input keyevent` for real key events
adb shell input keyevent KEYCODE_ESCAPE
```

## How it works

```
on-screen key / hardware key
        ↓
PinyinDuckSession        composition rules: buffer, candidates, selection   (no Android)
        ↓
InputConnection          commitText / deleteSurroundingText
```

| Layer | Files | Notes |
| --- | --- | --- |
| Composition | `ime/PinyinDuckSession.kt`, `ime/TextSink.kt` | No Android imports, so it is tested directly against a fake editor |
| Engine | `engine/*.kt` | A port of `packages/core`: pinyin parser, B+ tree reader, ranking |
| Dictionary | `data/DictionaryLoader.kt` | Maps the asset, no heap copy |
| UI | `ui/*.kt` | Jetpack Compose, drawn from one immutable `KeyboardUiState` |
| Service | `ime/PinyinDuckImeService.kt` | Window, editor, and the key routing that joins them |

### Why a Kotlin port instead of the web engine

`packages/core` is TypeScript, and the roadmap offered either bundling it into a JS engine
or porting it. This package ports it, for one concrete reason: **a lookup here is a
synchronous function call**. The B+ tree is mmap'd, so a page read is a pointer offset, so
`onKeyDown` can rank candidates and commit inside the same call.

Going through a JS engine would make every keystroke a bridge hop and a promise
microtask queue, and the engine's async `search()` would then be able to resolve out of
order relative to the keystrokes that produced it — the exact hazard `docs/roadmap.md`
describes for the web client.

The cost of a port is that the two implementations can drift. That is covered by a parity
test rather than left to discipline (see below).

### The dictionary is mmapped, never parsed

The APK stores `dictionary.btree` **uncompressed** (`noCompress += "btree"` in
`app/build.gradle.kts`). That is deliberate: compressing it would save about 5MB of APK,
but a compressed asset cannot be opened as a file descriptor, so the 9.1MB file would have
to be read into the heap — in a keyboard process, which is exactly what the paged format
exists to avoid.

At runtime the service maps the asset and reads only the 24-byte header, the page directory,
and the handful of pages a query touches, behind a 256KB LRU page cache. Resident cost is
the page cache, not the dictionary.

## Testing

```bash
cd packages/android
./gradlew test                       # tests
./gradlew jacocoTestReport           # coverage report
./gradlew check                      # tests plus the coverage floor
```

Runs JVM unit tests against the **real** 9.1MB dictionary, not a fixture — the whole point
of the ranked corpus is which candidate wins, and a small fixture would let the ranking
rules rot while every assertion still passed.

| Suite | Covers |
| --- | --- |
| `PinyinEngineParityTest` | The Kotlin engine reproduces the TypeScript engine's output exactly |
| `PinyinDuckEngineOptionsTest` | Paging, `exactOnly`, scan budgets, tone filters, script selection |
| `BTreeCodecTest` | Varints, page decoding, and every malformed-input path |
| `PageSourceTest` | mmap ranges, clamping, and the reader over a synthetic tree |
| `PinyinParserTest` | Segmentation, tone marks, umlauts, digit handling |
| `PinyinDuckSessionTest` | Composition rules against a fake editor |
| `KeyRoutingTest` | Physical key codes mapped to actions, and which keys are passed on |
| `KeyboardTest` | The Compose keyboard: every key, the candidate strip, the expanded panel |
| `PinyinDuckImeServiceTest` | The service end to end: dictionary load, key routing, lifecycle, teardown |
| `SettingsActivityTest` | The settings screen, and the script preference round-tripping |
| `DictionaryLoaderTest` | Opening the mapped asset out of the APK, and its failure modes |
| `KeysTest` | Key layouts: reachability, core keys, shift behaviour |

The Compose and activity suites run under **Robolectric**, so the whole app is covered from
the JVM — no device or emulator is needed to run `./gradlew check`.

### Coverage

Jacoco measures the whole module and writes HTML plus XML to
`app/build/reports/jacoco/jacocoTestReport/`. Open
`app/build/reports/jacoco/jacocoTestReport/html/index.html` to browse it per class.

Current state: **92% instruction coverage** (10,469 of 11,351 instructions), 207 tests.

`./gradlew check` enforces two floors:

- **80% instruction coverage across the whole module**, so the headline claim is checked by
  the build rather than observed once and remembered.
- **85% instruction *and* branch coverage, per class**, on the portable half:

```
dev.pinyinduck.android.engine.PinyinKt              the parser
dev.pinyinduck.android.engine.PinyinDuckEngine      search
dev.pinyinduck.android.engine.BTreeDictionary*      the reader
dev.pinyinduck.android.engine.BTreeCodecKt          the wire format
dev.pinyinduck.android.engine.ByteReader            varints and string decoding
dev.pinyinduck.android.engine.RankingKt             the scoring rules
dev.pinyinduck.android.engine.MappedPageSource      the mmap source
dev.pinyinduck.android.ime.PinyinDuckSession        composition rules
dev.pinyinduck.android.ui.KeysKt                    key layouts
```

The per-class floor is the strict one because these are the classes where a branch is a real
decision — a tone filter, a scan budget, a page boundary. The module-wide floor is on
instructions only, and deliberately so: the Compose compiler emits branches for recomposition
and stability checks that no test can drive, so a module-wide *branch* floor would be
measuring the compiler rather than this code. Branch coverage is still enforced, at the same
85%, everywhere it is meaningful.

### What a JVM test still cannot reach

There is no `ShadowInputMethodService`, so `currentInputConnection` is always null under
Robolectric. `PinyinDuckImeServiceTest` therefore asserts on the state the service owns —
composition, candidate selection, layout, lifecycle — and not on the text the keyboard would
have committed. Verifying the committed text means an instrumentation test on a device, which
is the one thing in this project that is not automated yet.

### The parity test

Because `packages/android` ports the engine rather than sharing it, a change to the ranking
rules in `packages/core` could silently reorder candidates on Android only, with nothing
failing. `packages/core/scripts/generate-android-parity.ts` runs the real TypeScript engine
over the real dictionary for 26 pinned queries and writes what it found to
`app/src/test/resources/engine-parity.tsv`; the Kotlin test asserts it reproduces that file
exactly — same ordering, same tone marks, same glosses, same totals.

**Re-run it whenever the ranking rules or the dictionary change:**

```bash
npm run build:parity     # from the repository root: regenerate and commit the golden file
cd packages/android && ./gradlew test   # assert the Kotlin engine still matches
```

## Troubleshooting

**The keyboard never appears in the list.** It must be both installed *and* enabled; see
[Enable it](#enable-it). Uninstalling and reinstalling usually clears a stale registration.

**Every candidate is missing and the bar says the dictionary is unreadable.** The asset did
not make it into the APK. Run `npm run build:dict` at the repository root, then rebuild.

**"The dictionary asset is compressed."** `noCompress += "btree"` was lost from
`app/build.gradle.kts`. A compressed asset cannot be mmapped.

**A broad syllable like `ta` shows a long list.** It has 1,476 candidates. Use the page
arrows, or open **▴** for the full list.

**Typing a digit inserts a tone filter instead of the digit.** That is intentional while a
composition is active. Finish or clear the composition first with space, **✕** or a
letter that continues it.

**The on-screen keyboard covers a lot of the screen.** Use **▴** to inspect the full
candidate list, then collapse it again with **▾**.
